# Как это устроено / How it works

## Схема / The map

```
   ТЫ / YOU                    СЕРВЕР / YOUR SERVER
  ┌─────────┐
  │ Telegram│◄──────────┐
  └────┬────┘           │  ответы (reply) + зеркало в лог
       │ сообщения      │  replies + mirror to log
       ▼                │
  ┌─────────────────────┴──────────────────────────────────┐
  │  tmux-сессия "telegram"                                 │
  │  ┌──────────────────────────────────────────────────┐   │
  │  │  claude --channels plugin:telegram --resume <id>  │   │
  │  │  (полный доступ: файлы, bash, агенты, MCP)        │   │
  │  └───────────────┬──────────────────────────────────┘   │
  │                  │ порождает                            │
  │            ┌─────▼──────┐                               │
  │            │ bun server │ ← опрашивает Telegram getUpdates
  │            │  (плагин)  │   ⚠ ровно ОДИН на токен!      │
  │            └────────────┘                               │
  └─────────────────────────────────────────────────────────┘
                       ▲
                       │ проверяет и лечит каждые 3 минуты
              ┌────────┴─────────┐
              │    watchdog      │ ← cron */3
              │  7 проверок      │
              └────────┬─────────┘
                       │ если не чинится
                       ▼
              ┌──────────────────┐
              │  notify-owner    │ → прямой Bot API, минуя всё
              └──────────────────┘
```

## Почему именно так / Why this shape

**Почему tmux, а не systemd-сервис?**
Агент — интерактивная TUI-программа, а не демон. В tmux она живёт как за клавиатурой: можно
подсмотреть экран (`capture-pane`), послать ввод (`send-keys`), пережить обрыв SSH. Systemd
поверх этого — опционально (`core/claude-telegram.service`), но cron+tmux проще и надёжнее
для интерактива.

**Почему сторож в cron, а не внутри агента?**
Сторож должен пережить смерть агента. Всё, что живёт внутри процесса, умирает вместе с ним.
Cron — единственная часть системы, которую не может убить сам агент.

**Почему `--resume <id>`, а не `--continue`?**
`--continue` берёт последнюю тронутую сессию в каталоге проекта — а там бывают чужие
(ручные запуски, фоновые агенты). Резолв конкретного `session_id` по транскрипту канала
гарантирует, что после рестарта продолжится ИМЕННО ваш разговор.

**Почему зеркало ответов в лог?**
Telegram — единственная точка отказа для связи. Зеркало (`conv-mirror.sh`) пишет каждый
ответ в файл с меткой доставки, поэтому при падении канала владелец видит разговор через
`tail -f`, а не гадает.

**Почему отдельный путь `notify-owner.sh`?**
Он работает от токена бота напрямую, минуя Claude, плагин и сессию. Когда лежит всё
остальное, это последний живой провод к владельцу.

## Семь проверок сторожа / The watchdog's seven checks

| # | Проверка | Что ловит |
|---|---|---|
| 1 | tmux-сессия существует | сессия убита/не поднялась |
| 3 | процесс claude жив в сессии | процесс умер, окно осталось |
| — | детектор лимита подписки | «You've hit your session limit» → ждать до сброса, не рестартить |
| 4 | плагин (bun) жив | плагин упал — сообщения не доходят |
| 5b | нет процессов-сирот | зомби ворует очередь (409 Conflict) |
| 5 | плагин не «заморожен» | процесс жив, но потерял соединение с Telegram |
| 6 | нет тихого отказа | сообщение принято, ответа нет, признаков работы нет |
| 7 | доступ к модели | подписка кончилась / разлогин |

Лестница лечения: обычный рестарт → чистый рестарт (теряя контекст) → пауза с эскалацией
владельцу. Гейт лимита стоит выше всего: под лимитом рестарты бессмысленны.
